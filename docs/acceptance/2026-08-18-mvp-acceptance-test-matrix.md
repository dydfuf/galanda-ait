## 3. 테스트 데이터와 초기화

### 3.1 기본 실행 프로필

환경 변수 `VITE_USE_SUPABASE=true`가 없으면 `LocalProfile`을 사용한다.

- 세션: `user-local-me` / `나` / 인증됨
- 기본 역할: 생성 시 `HOST`
- 여행방 저장 키: `galanda_rooms_v1`
- 편집 임시안 키: `galanda_draft_<roomId>_<new|planId>`
- 로컬 저장소는 브라우저 한 기기 안에서만 공유되며 다중 사용자 보안 경계를 재현하지 않는다.

### 3.2 초기화

브라우저 콘솔 또는 `agent-browser eval`에서 실행한다. 앱 전체 `localStorage.clear()`는 앱인토스 개발 키를 지울 수 있으므로 사용하지 않는다.

```js
localStorage.removeItem("galanda_rooms_v1");
Object.keys(localStorage)
  .filter((key) => key.startsWith("galanda_draft_"))
  .forEach((key) => localStorage.removeItem(key));
location.href = "/trips";
```

초기화 직후 기대 결과는 `TR-01`의 `아직 참여 중인 여행이 없어요`와 `새 여행 만들기`다.

### 3.3 정상 fixture 만들기

초기화 후 다음 순서로 같은 fixture를 만든다.

1. `TR-01`에서 `새 여행 만들기`를 선택한다.
2. 여행 이름을 `RAON-141 smoke 여행`으로 입력하고 만든다.
3. `PL-01`의 `첫 여행안 만들기`에서 제목을 `A안 기본 여행`으로 입력한다. 숙소는 `숙소 찾는 중`, 교통은 기본값으로 둔 채 공개한다.
4. `PL-01`에서 `새 여행안 제안하기`를 선택하고 제목을 `B안 대안 여행`으로 입력해 두 번째 공개안을 만든다.
5. `여행안 비교하기`에서 A안을 선택한 채 확정한다. 브라우저 native confirm은 `확인`으로 닫는다.
6. `IT-01`에서 확정 배너, `확인할 내용`, 날짜별 일정과 검토 기록을 확인한다.

가격 범위는 PL-03의 숙소 또는 교통에 최소·최대 원화 값을 각각 넣어 `480~520만원`처럼 검증한다. 날짜 미정은 시작일 또는 종료일을 비워 공개 CTA가 활성화되지 않는지 확인한다. draft 복원은 PL-03에서 제목을 입력하고 뒤로 나갔다가 같은 편집 경로로 다시 들어가 입력값을 확인한다.

### 3.4 역할 fixture의 한계

현재 `LocalSessionLayer`는 항상 `user-local-me`를 반환하고 UI에는 역할 전환 기능이 없다. 따라서 `H/M/G` 화면 smoke는 이 문서만으로 재현할 수 없다. 역할 전환이 추가되기 전에는 다음을 구분한다.

- `H`: 기본 로컬 smoke로 실행
- `M`: 멤버 세션 또는 Supabase JWT가 있는 환경에서 수동 실행
- `G`: 로그인하지 않은 초대 링크 환경에서 수동 실행
- 도메인 권한 규칙·revision 충돌: fake repository/session을 사용하는 자동화 대상으로 분리

#### 초대 capability 계약 (2026-08-24)

- Trip마다 활성 초대는 하나이며 발급 후 7일 동안 여러 참여자가 재사용할 수 있다.
- 재발급은 같은 Trip의 이전 토큰을 즉시 무효화하고, 폐기는 여러 번 호출해도 같은 결과다.
- 원문 token은 발급 응답과 공유 URL에만 존재한다. DB에는 SHA-256 hash만 저장한다.
- `GET /api/invites/:inviteToken`은 `title`, `inviterName`, `participantCount`, `alreadyJoined`만 기본 반환한다. 확정 여행안이 있을 때만 `destination`, `startDate`, `endDate`를 추가한다.
- malformed, missing, expired, revoked token은 모두 `404 INVITE_INVALID`로 응답하고 token이나 Trip 정보를 오류에 포함하지 않는다. 저장소·인증 장애는 재시도 가능한 `503`이다.
- `POST /api/invites/:inviteToken/join`은 nickname만 받고 id·role·tripId는 session/token에서 결정한다. invite와 Trip row를 함께 잠가 검증과 membership CAS를 한 transaction에서 처리한다.
- 직접 `POST /api/trips/:tripId/join` 경로는 제거한다. 같은 session의 중복 제출·네트워크 재시도는 membership을 추가로 쓰지 않고 기존 Trip을 반환한다.
- 링크 조회만으로 user/session/membership은 생성되지 않는다. 수락 시에만 기존 Better Auth anonymous session을 보장하고, nickname은 auth profile이 아닌 `TripMember.name`에 저장한다.

## 6. 자동화와 수동 확인 분리

### 자동화 우선 후보

- `createTripRoom`: 제목·날짜 검증, 한 번만 생성
- `createPlan` / `updatePlan`: 제목·기준 인원·공개 조건·가격 범위·draft와 공개본 분리
- `calculatePlanDifference`: 복제안의 날짜·도시·예약·비용 차이
- `getRoomActor`와 권한 guard: `H/M/G`별 action 허용 여부
- repository: revision 충돌, 확정의 멱등성, 의견 upsert, 중복 참여 방지
- route parameter: 잘못된 `tripId`, `planId`, `inviteToken` 차단

### 수동 확인 우선 항목

- TDS CTA의 위치·문구·비활성·로딩 상태
- 화면 전환과 뒤로가기, 확정 후 기본 탭
- 가격 범위·날짜 미정·예약 위험의 실제 표시 밀도
- 클립보드 초대 링크, native confirm, 토스 로그인·WebView 권한
- 브라우저 새로고침 후 LocalStorage draft와 목록 복원
- 참여자 화면에서 방장 전용 CTA가 보이지 않는지
